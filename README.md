# TMS570 FreeRTOS

This project is an embedded FreeRTOS application for the TMS570 platform. The main application logic lives in [source/App.cpp](source/App.cpp), where the system is initialized, RTOS objects are created, and the scheduler is started.

The code is centered around three main layers:

- HALCoGen-generated peripheral and RTOS setup.
- The FreeRTOS application layer in [source/App.cpp](source/App.cpp).
- External libraries for framing, serialization, and XBee communication.

## Project Layout

- [source/](source/) contains the application code and HALCoGen-generated driver sources.
- [include/](include/) contains headers for the application, FreeRTOS, HALCoGen, and driver interfaces.
- [cobs/](cobs/) contains COBS encoding and decoding helpers.
- [msgpack/](msgpack/) contains the MessagePack dependencies.
- [xbee/](xbee/) contains the Digi XBee API submodule used by the RF task.

## Application Overview

Task control blocks and stacks are defined in the application resource block (`xAppResources`) to avoid runtime heap usage for the main RTOS objects.

### Task Model

The main tasks are organized by priority:

- `Init` performs post-scheduler initialization that requires interrupts.
- `DataUpdate` processes CAN data and refreshes the dashboard state.
- `Rules` evaluates safety and compliance logic.
- `DriversFSM` manages driver-state decisions.
- `RFDataRx` receives XBee packets, decodes them, and dispatches commands.
- `Cmd` handles command processing.
- `Telemetry` packs telemetry and transmits it over XBee.
- `Display` refreshes the GUI.

Some tasks are present as placeholders or temporarily disabled in the source, but the scheduling model is already laid out around those roles.

### Synchronization and Communication

The application relies on FreeRTOS primitives instead of queues for most data flow (to keep ISRs as short and simple as possible):

- `EventGroup` for task wake-up and inter-task signaling.
- `Mutex` for protecting shared snapshots of application data.
- `Software timers` for (optionally) deferred startup actions and telemetry timeout handling.

The event bits are used to model periodic events and asynchronous notifications. For example, periodic data, telemetry, UI, and display updates are represented as event flags, while RF and telemetry acknowledgements use separate flags for command dispatch.

### Initialization

`vAppInitModules()`, configures the peripherals before the scheduler starts. In the current implementation it initializes CAN, GIO, SCI, SPI, EEPROM/Flash access through TI FEE, the display, and the dashboard/data structures. Once the scheduler is running, `vInitTask()` (optionally) calls `vAppInitModulesWithInterrupts()` to cofigure drivers that require interrupts to be enabled before they can be used.

### OS and Tick Integration

The FreeRTOS port is backed by the TMS570 RTI peripheral. In [source/os_port.c](source/os_port.c) (`prvSetupTimerInterrupt()`), the scheduler setup programs RTI counter 0 compare 0 as the system tick source using `configCPU_CLOCK_HZ` and `configTICK_RATE_HZ`. Other counter blocks and compare registers should be configured there as well (not using `rtiInit()`).

## Submodules

External libraries:

- [cobs/cobs-c](cobs/cobs-c) for COBS encoding/decoding.
- [cobs/nanocobs](cobs/nanocobs) for the compact COBS implementation.
- [msgpack/msgpack-c](msgpack/msgpack-c) for MessagePack serialization.
- [msgpack/cmp](msgpack/cmp) for MessagePack-compatible packing helpers.
- [xbee/digi_xbee_api](xbee/digi_xbee_api) for XBee API frame handling.

After cloning, initialize them with:

```bash
git submodule update --init --recursive
```
